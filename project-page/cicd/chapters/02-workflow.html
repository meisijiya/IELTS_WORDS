触发条件与依赖关系

Workflow 位于 .github/workflows/deploy.yml，只在 main 分支 push 或手动触发时运行。来源：§2。 

on:
  push:
    branches: [main]
  workflow_dispatch:

两个 job 不是并行关系。deploy 声明 needs: build-and-push， 因此只有镜像构建和推送成功，服务器部署才会开始。

build-and-push job

这个 job 在 GitHub 托管的 ubuntu-latest runner 上执行。来源：§2.1。

  1. actions/checkout@v4 拉取当前提交源码。
  2. docker/setup-buildx-action@v3 准备 BuildKit buildx。
  3. docker/login-action@v3 使用 Secrets 登录阿里云 ACR。
  4. Extract version 计算短 SHA 与时间戳。
  5. docker/build-push-action@v6 构建并推送镜像。
  6. 以 inline 形式写入 OCI cache metadata。
Tag用途
meisijiya/yasi-words:latestdeploy job 默认拉取
meisijiya/yasi-words:<short-sha>精确定位提交与回滚
meisijiya/yasi-words:<timestamp>按构建时间追踪历史
关键结果：这个 job 的交付物不是压缩包，也不是服务器目录中的源码，而是 ACR 中可按 tag 拉取的容器镜像。

deploy job

这个 job 同样运行在 GitHub runner 上，但真正的部署命令由 appleboy/ssh-action@v1 发送到服务器执行。来源：§2.2。 

set -e
cd /opt/yasi-words

echo "$ALIYUN_REGISTRY_PASSWORD" | docker login \
  -u "$ALIYUN_REGISTRY_USERNAME" \
  --password-stdin "$ALIYUN_REGISTRY"

export APP_IMAGE="$ALIYUN_REGISTRY/$ALIYUN_REGISTRY_NAMESPACE/yasi-words:latest"

docker pull "$APP_IMAGE"
docker compose pull app
docker compose up -d --force-recreate app
docker image prune -f --filter "until=24h"

逐行理解

  • set -e 让任何失败命令立即终止部署。
  • docker login 让服务器获得拉取 ACR 镜像的权限。
  • APP_IMAGE 把完整 registry、namespace、仓库与 tag 交给 Compose。
  • docker pull 明确拉取目标镜像，避免把 server build 当成 fallback。
  • --force-recreate app 用新镜像替换应用容器，不重建 PostgreSQL。
  • docker image prune 清理较旧的未使用镜像，控制磁盘占用。

Workflow 还会执行 5 次 sleep 与 curl 的健康检查，总等待上限约 1 分钟。

为什么 Compose 必须有 image:

如果 app service 只有 build:，docker compose pull app 会提示没有可拉取镜像并跳过。随后 up --force-recreate 可能在服务器上重新 build， 整条 ACR 分发链路被绕过。来源：§2.3。

错误配置：

app:
  build:
    context: .

项目需要的配置：

app:
  image: ${APP_IMAGE:-}
  build:
    context: .

部署时，workflow 导出 APP_IMAGE，Compose 得到明确远程镜像；本地开发不设置它时， build: 仍然可用。一个 service 同时保留两种入口，但生产部署必须沿着 image: 走。

验证原则：docker compose pull app 成功并不等于服务已重启， 还必须执行 docker compose up -d --force-recreate app 并通过健康检查。
